# Graph accuracy: evaluation protocol

Written before any measurement. Every finding swift-modularity reports (cycles, Core membership,
references to remove) rests on its file dependency graph, which is built from syntax alone. This
evaluation measures how close that graph is to the dependencies the compiler resolves.

## Question

For the Swift files of one module, how do the edges of `FileDependencyGraphBuilder` (file A
depends on file B) compare with the edges in the compiler's index, and how much do the
structural results (cyclic groups, Core, propagation cost) change?

## Ground truth

The index store written by the compiler (`swift build` on macOS, or Xcode's
`Index.noindex/DataStore`), read with IndexStoreDB.

For each file F of a module, every symbol occurrence in F whose roles include `reference` and do
not include `implicit`, `definition` or `declaration`, is resolved to the files where the symbol
is defined (occurrences with the `definition` role). F depends on G when G ≠ F and G is a file of
the same module.

- **T_all**: every such edge.
- **T_scope**: edges with at least one reference to a symbol of a kind the tool claims to
  resolve: types (struct, class, enum, protocol, typealias), free functions, global variables and
  macros. Edges created only by members (methods, properties, enum cases, initializers, members
  added by extensions) are outside the scope; the README documents them as not resolved.

Known limits of the ground truth: protocol requirement calls resolve to the requirement, not to
the implementation; code generated by macros is not counted; implicit references (synthesized
conformances, property wrapper storage) are excluded.

Modules where the index is older than any of its files are skipped and reported (stale index).
Modules with fewer than 2 files are skipped.

## Measures

Per module and pooled over all modules (micro-average):

- Edge **precision** = |tool ∩ T_all| / |tool| (a tool edge that the compiler does not see is an error).
- Edge **recall** against T_all, and against T_scope (recall within the documented scope).
- Structure, from `ModularityAnalysis` on the tool graph and on T_all:
  - propagation cost, size of the largest cyclic group, number of cyclic groups, architecture type;
  - pairwise **co-membership** precision and recall: over pairs of files, "in the same cyclic
    group" in the tool graph versus in T_all;
  - agreement of Core membership and of the partition group of each file.

## Error analysis

Every false positive edge and a sample of false negative edges are classified by cause, with the
reference the tool or the index gives.

## Corpus

Chosen by whoever runs the evaluation, among code they may analyze. Test modules are included as
separate modules, since tests are code the tool will be run on. The corpus and the results are
never committed: `results/`, `RESULTS.md` and any script naming the corpus are gitignored, because
they describe the repositories evaluated.

## Rules

- swift-modularity is evaluated at the commit under review. It is not changed during the
  evaluation; improvements found here are made afterwards and measured
  separately.
- All modules that meet the conditions above are reported, whatever their results.
